# Root Cause Analysis: Duplicate Field Names in erp_fields Table

## Issue Summary
The `/api/fields/{entityType}` endpoint was returning 546 rows for 21 unique field names, indicating **~26x duplication** of data.

## Root Cause

### The Problem Chain

1. **Schema Generation Mismatch**
   - Application uses `spring.jpa.hibernate.ddl-auto=create-drop` in dev mode
   - Hibernate generates schema from JPA entities on each startup
   - **`ErpField.java` was MISSING `@UniqueConstraint` annotation**
   - Result: Database created **WITHOUT** unique constraint on `(entity_type, field_name)`

2. **Data Initialization Logic Depends on Unique Constraint**
   - `MasterDbSystemDataInitializer.loadErpFields()` uses:
   ```sql
   INSERT INTO erp_fields (...) VALUES (...)
   ON DUPLICATE KEY UPDATE 
     field_label = VALUES(field_label),
     ...
   ```
   - **`ON DUPLICATE KEY UPDATE` only works when there's a unique constraint!**
   - Without constraint: Creates new row every time instead of updating existing row

3. **Startup Sequence Creates Duplicates**
   - On first startup: Loads 21 fields from XML files
   - On second startup: 
     - Hibernate drops and recreates tables (no unique constraint)
     - Data initializer runs again
     - `ON DUPLICATE KEY UPDATE` fails to detect duplicates (no constraint)
     - Inserts another 21 rows → Total: 42 rows
   - After 26 startups: 546 rows

4. **Tenant Provisioning Also Affected**
   - `TenantProvisioningService.copySystemData()` uses `INSERT IGNORE`
   - Without unique constraint, `INSERT IGNORE` doesn't prevent duplicates properly
   - Tenant databases would also accumulate duplicates

## Why SQL Scripts Had the Constraint

- `scripts/iam_master_system_tables.sql` **HAS** the constraint:
  ```sql
  UNIQUE KEY unique_entity_field (entity_type, field_name)
  ```
- But this script is NOT used when `ddl-auto=create-drop`
- Hibernate generates schema from JPA entities, ignoring these SQL files

## The Solution

### ✅ Added `@UniqueConstraint` to `ErpField` Entity

```java
@Entity
@Table(name = "erp_fields", uniqueConstraints = {
    @UniqueConstraint(columnNames = {"entity_type", "field_name"})
})
public class ErpField extends BaseEntity {
    // ...
}
```

### Why This Is The Correct Fix

1. **Hibernate Schema Generation**: Now includes unique constraint when creating tables
2. **`ON DUPLICATE KEY UPDATE` Works**: Can detect duplicates and update instead of insert
3. **Data Integrity**: Database enforces uniqueness at schema level
4. **Tenant Provisioning**: `INSERT IGNORE` works correctly
5. **Future-Proof**: Even if initialization runs multiple times, no duplicates

### Additional Fixes Applied

1. **Dropped Existing Databases**: Forced clean recreation with new constraint
   ```sql
   DROP DATABASE IF EXISTS IAM_MasterDB;
   DROP DATABASE IF EXISTS ERP_Dev_Tenant_1;
   ```

2. **Reverted Temporary Workarounds**:
   - Removed `DISTINCT` keywords from repository queries
   - Removed service-layer deduplication logic
   - These were treating symptoms, not root cause

## Schema Comparison

### Before (Generated by Hibernate WITHOUT @UniqueConstraint)
```sql
CREATE TABLE erp_fields (
    erp_field_id BIGINT PRIMARY KEY,
    entity_type VARCHAR(250) NOT NULL,
    field_name VARCHAR(100) NOT NULL,
    -- ... other columns
    INDEX idx_entity_type (entity_type),
    INDEX idx_field_name (field_name)
    -- NO UNIQUE CONSTRAINT!
);
```

### After (Generated by Hibernate WITH @UniqueConstraint)
```sql
CREATE TABLE erp_fields (
    erp_field_id BIGINT PRIMARY KEY,
    entity_type VARCHAR(250) NOT NULL,
    field_name VARCHAR(100) NOT NULL,
    -- ... other columns
    INDEX idx_entity_type (entity_type),
    INDEX idx_field_name (field_name),
    UNIQUE KEY UK_entity_field (entity_type, field_name)  -- ✅ NOW PRESENT
);
```

## Lessons Learned

1. **Always Define Constraints in JPA Entities**
   - When using `ddl-auto=create-drop`, Hibernate ignores SQL scripts
   - Constraints must be defined using JPA annotations

2. **`ON DUPLICATE KEY UPDATE` Requires Unique Constraint**
   - Without constraint, MySQL cannot detect duplicates
   - Always verify unique constraint exists before using this syntax

3. **Symptoms vs Root Cause**
   - Query-level fixes (DISTINCT, deduplication) only hide the problem
   - Database-level constraints prevent bad data from being created

4. **Data Initialization Must Be Idempotent**
   - With `create-drop`, initialization runs on every startup
   - Code must handle re-runs gracefully (using proper constraints)

## Verification

After fix, on next startup:
- Hibernate creates `erp_fields` table with unique constraint
- `MasterDbSystemDataInitializer` runs and loads 21 fields
- Second startup: Same 21 fields, but `ON DUPLICATE KEY UPDATE` works correctly
- Result: **21 rows** instead of **546 rows** ✅
